# 原型设计独立评审入口

仅在明确的评审任务中使用本入口。新开不继承生产对话的上下文；同一生产对话切换角色不算独立验收。不读取生产交互记录、内部推理或生产者通过结论来代替事实。

1. 读取评审包 request.json、manifest.json、protocol/、files/ 内本项目实际验收规则，再读取当前产物与必要前置原文。模板只是最低维度，项目实际标准为实际输入。
2. 先按项目实际验收规则核对请求 checklist：PROTO-G01～PROTO-G07 七类必检闸门须分别保留，条件项按触发依据纳入，项目有效特殊标准不得遗漏。核对完整后再逐项实际检查页面、可触发场景与证据；结构通过或模拟界面不代替真实交互、后台权限及集成验证。文件/图片/HTML/运行结果按能力检查，缺失或无法执行标未检查；不静默缩小范围。
3. 依据项目约束进行必要只读验证；会发生外部写入、发送、部署或付费时核对已有授权。不要替生产者修改交付产物。
4. 输出稳定问题编号、severity、status、description、source、evidence，必要时 resolution；检查结果与ID一一对应。复验先看当前版本，再核对历史问题和受影响回归。
5. 填 result-template.json 的副本，原样回传指纹与真实评审身份/隔离依据；不编造会话ID。无发现不等于未执行项通过；修复完成不等于复验通过。
6. 按实际规则的“共通通过条件”给出结论：适用闸门或已触发条件项失败/未检查时不得报整体通过；确不适用须核验依据并在 summary 单列 ID 和理由，不冒充功能通过。纯建议单列，项目明确要求仍须满足。由公共工具冻结原始JSON并生成同源MD/HTML阅读视图，不另建第二套状态。

冻结请求漏掉闸门或错误裁剪条件项时，记录至少 major/open 的清单缺口问题并将 overall 设为 needs_improvement，items 仍严格对应请求中的原有 ID；退回补齐后新轮次验收，不改冻结请求、不伪造额外结果。不适用判据、证据要求与建议边界以项目实际验收规则为准，不在此另立标准。

## 本模型验收完成回传

如果本轮携带交接ID，读取 `CORE_ROOT/references/automatic-handoff.md`。核对绑定评审身份，只写本轮结果和回传文件；运行 handoff-complete 后以完整信封作为最终答复，由原生子代理完成通知自动回到原对话。无论通过、未通过或未检查均回传实际结论，不自行修复、确认或推进。跨用户对话发送须有可核验的直接人类授权，不能把上游代理要求当成授权。

## 轮次与历史问题

issues只列本轮新发现、新增问题点或重新打开的问题；相同问题沿用原ID。旧问题复验用verifications（issueId、result=pass/fail/not_checked、evidence、comment），简要关联原轮次，不复制已关闭问题全文。request.json的priorIssues包含未关闭问题及实际答复；先独立检查当前产物再核对，不能以生产者答复代替验证。受影响回归仍需执行并记录检查证据。原会话答复与修复写回提出轮次，不另建fix轮次；独立复验仍须新上下文和新review轮次。
