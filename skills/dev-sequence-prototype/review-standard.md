# 原型设计验收规则

适用范围：本期已声明产物及其必要基线。保留项目特殊标准。原型阶段核对界面是否真实呈现、交互能否演示；业务规则以有效 PRD 为准，模拟界面不证明后台权限、真实集成或模型质量。

## 七类必检闸门

以下七类须逐项核对适用性及所有适用内容，不得抽查、删除、合并为一个笼统结论，或以原有综合条目替代。证据须定位到实际 PRD、页面/模块/场景及观察结果；只有截图文件名、代码存在或结构校验通过不足以证明交互正确。

| 检查ID | 等级 | 类别 | 验收标准与最低证据 |
|---|---|---|---|
| PROTO-G01 | 必检闸门 | 页面覆盖 | 对照 PRD 本期需求及页面/视图清单，全量核对注册页面、模块、弹窗与关键场景；无界面需求有合理说明及其他验证引用。证据逐条列出对应与缺口，不能因未制作而删掉应有页面。 |
| PROTO-G02 | 必检闸门 | 权限 | 适用角色、操作/字段、数据范围及允许/禁止场景的界面表现与 PRD 一致，可重复展示关键角色差异。证据包含演示步骤与实际观察；明确模拟角色切换不构成后台鉴权证据。 |
| PROTO-G03 | 必检闸门 | 异常与失败 | 关键流程的主要失败、中断及恢复有可重复触发方式，失败反馈、输入保留、最终状态和重试/取消符合 PRD；超时、重复提交、冲突或部分成功按实际风险检查。证据记录触发、实际结果与恢复路径，明确模拟边界。 |
| PROTO-G04 | 必检闸门 | 空态与加载态 | 适用页面/异步操作的默认、加载、无数据/无结果与错误状态可区分并可重复触发，后续动作及退出等待符合 PRD。证据记录各适用状态入口和实际观察；不能只写“支持空态/加载态”或以提交成功代替加载态。 |
| PROTO-G05 | 必检闸门 | AC 关联 | 每条本期有界面功能关联的正常及关键异常 AC 能定位到可演示的页面/模块/场景，并按前置数据、动作、预期与实际结果核对。后台/真实集成 AC 标明其他验证入口，不将原型演示当作真实测试通过。 |
| PROTO-G06 | 必检闸门 | 追溯完整 | PRD 的需求/规则/页面/AC 与配置权威映射、实际模块锚点和场景全量对账，引用存在且语义相符；无界面项说明与证据完整，遗漏和部分覆盖显式登记。证据包含对账清单及引用校验结果，结构通过不替代业务覆盖判断。 |
| PROTO-G07 | 必检闸门 | 版本一致 | PRD 当前版本、原型业务版本及绑定关系有效；独立规范、变更记录与本期内容一致，构建产物的框架版本、指纹和 buildId 与当前源一致。证据注明实际版本与源/产物校验结果，不能复用旧构建的通过结论。 |

## 条件项与既有编号

保留 PROTO-01～PROTO-06 的原有含义，不重编号。发起前逐项判断触发条件：触发后进入本轮 checklist，按实际页面/终端/载体展开；未触发的条目在请求 instructions 中列出 ID、理由及基线依据，不进入执行清单。与闸门重叠的内容引用同一证据，不重复造表或另建业务规则。

| 检查ID | 等级 | 触发条件 | 验收标准 |
|---|---|---|---|
| PROTO-01 | 条件项 | 本期有需求/规则/AC 的原型映射或无界面说明。 | 本期 FR/规则/AC 对应页面模块和可触发场景；无界面需求有不适用理由及其他验证引用。 |
| PROTO-02 | 条件项 | 本期包含页面、浮层、字段、状态或权限呈现。 | 页面、弹窗、字段、默认值、状态与权限表现和需求一致，交互可实际走通。 |
| PROTO-03 | 条件项 | 包含校验、提交、异步操作、失败或恢复交互。 | 校验、提交中、真实成功、失败/超时及适用恢复可区分，模拟边界与重置可复现。 |
| PROTO-04 | 条件项 | 使用原型注册表、独立规范或统一框架构建。 | 注册表/独立规范/稳定锚点及统一框架/业务版本正确，源与产物校验通过。 |
| PROTO-05 | 条件项 | 原型使用浏览器运行；按实际长短页、终端、标注、画布及浮层功能展开适用子项。 | 浏览器实际检查长短页、终端切换、真实高度、标注、拖拽/滚动和浮层生命周期，证据可查。 |
| PROTO-06 | 条件项 | 存在对应 UI 约定、页面/模块说明、统计、术语、FAQ、变更记录或埋点要求。 | UI 规范、页面/模块说明、业务端统计、术语、FAQ、作者确认的变更记录和埋点说明完整一致。 |

## 共通通过条件

- 先检查七类闸门及条件项是否完整进入实际请求，再检查产物。遗漏闸门、错误裁剪条件项或缺少必要证据时不得判通过；已冻结清单有遗漏时，报告中登记阻塞问题，返回补齐请求后重新验收，不能修改冻结请求或伪造新增结果 ID。
- 适用的必检闸门或已触发条件项有 `fail` / `not_checked`，整体不能通过。修复尚未复验、版本/指纹失效或有未解决阻塞同样不能通过；不通过总分或其他条目通过来抵消。
- 七类闸门均保留适用性核对。确不适用时，evidence 写明实际基线位置、范围与理由，comment 以“不适用：”说明；`pass` 仅表示已验证该适用性判断成立，summary 单列不适用 ID 和理由，不宣称对应业务能力已验收。资料缺失、能力不足或未执行须写 `not_checked`，不能转成不适用。
- 结果沿用 `pass/fail/not_checked` 协议，不新增 N/A 枚举。纯视觉微调等非约定建议记为 suggestion，不塞入必过清单；已成为项目明确要求的视觉/无障碍标准仍须验收。正式豁免另行记录真实批准依据，不显示全部通过。
- MD与HTML同源，原始报告不可覆盖。独立评审与用户阶段确认分开；所有报告/请求/提示词存项目根验收记录目录。结构工具能校验清单结果、证据字段与状态，不能自动证明七类业务覆盖完整或适用性理由成立。

## 项目补充规则

执行者据真实范围补充，不以模板默认条目代替本期检查清单。模板中的七类闸门是最低要求，不替代项目其他有效标准。既有项目先对比合并实际规则，保留自定义内容，不自动覆盖或改写历史冻结记录；规则变化刷新受影响旧验收，新轮次绑定当前实际规则。
