# 最终测试验收强制隔离规则 v1.2

适用于 `test` 最终验收节点，包括单独调用、组合、全链路、手动第三方交接和授权自动化。最终测试必须在新会话中独立设计并实际执行，不能只在新会话审阅原生产者的测试报告。没有隔离或执行条件时不得改为原会话代测后宣称独立通过。

## 分工与输入

- 原会话只准备有效需求/AC、UI/原型与技术基线、待测代码/构建/配置、环境、账号权限、范围与已知风险。开发阶段自测仍允许，但不能代替最终独立验收。
- 派发应发生在本轮测试计划、执行和最终测试报告形成之前。请求的 artifacts 指向实际待测版本或版本清单，context 绑定实际代码；不要要求先有最终报告才能开始测试。
- 使用不继承生产历史的新上下文；只传必要权威基线、当前产物与适用历史缺陷，不附开发对话、推理、结论或自测“已通过”判断。
- 冻结输入只声明实际待测文件，不把将生成测试产物的整个项目目录当成输入，避免自身写入造成基线失效。测试输出放测试验收/，正式记录放验收记录/测试验收记录/的单轮MD/HTML；执行证据放该轮.过程/，内部账本放.dev-sequence/reviews/。

## 独立测试会话必须完成

1. 从需求、AC、风险和实际架构独立形成或修订计划、覆盖映射和TC。可以参考既有用例，但必须自行判断充分性并补齐适用场景，不能照搬勾选。
2. 实际执行必要测试，记录预期、实际、运行方法、环境、构建、日志和证据。Mock/静态检查/真实集成分开；没有执行能力的必需项明确 not_checked，不伪造成功。
3. 核对真实业务状态、缺陷与风险，独立生成业务测试报告及正式结果。只允许写测试计划、TC、测试脚本、证据和报告；不得改受测代码、需求或验收规则来让测试通过。
4. 通过结果包含 independentTest：本轮sessionId与reviewer.sessionId一致；freshContext/designedHere/executedHere为true；designEvidence、executionEvidence、testCaseIds、buildVersion、environment齐全。evidenceFiles须包含design与execution的实际非空文件及SHA-256，工具检查存在性和指纹；内容是否有效仍须实际核验。

## 强制闭环

新测试会话独立设计/执行 → 自动回传原会话 → 原会话核对并修复 → 生成新待测版本/新review轮次 → **再开一个全新会话**独立复验及受影响回归 → 回传结果。

复验不得复用生产会话、上一轮或任何历史测试会话。可以把冻结的历史缺陷作为prior-review输入，但不能把历史测试上下文fork成复验会话。原会话通过reply在问题提出轮次登记修复和实际证据，不额外建立fix轮次；复验仍创建新review轮次并派发另一个全新会话。历史fix记录只登记处理，不是测试验收通过。

同一轮因派发失败重新交接时也必须创建新的测试会话，不能复用失败交接曾绑定的身份；绑定时核对实时交接历史，直接导入结果也不能绕过失败身份检查。

prepare为test强制登记实际producer-session，并将已知生产/测试会话及已派发测试标识写入冻结的independentTestPolicy；handoff-bind和结果导入拒绝复用。规则不能由自定义请求删掉。通过结果缺独立设计/执行及真实证据，或仅script检查，不能通过；未执行时允许真实失败/未检查结果正常回传，不能以“缺条件”为由无声中断。

自动回传、修复、补证、暂停恢复和按授权自动确认沿用automatic-handoff.md。缺少必要资料、权限、隔离工具或存在规则冲突时，只暂停受影响动作并说明；有明确自动化授权且条件充分时不反复要求用户发送“继续”。

这是最终测试执行与产出本身的强制要求，比“新会话审阅测试报告”更严格。工具校验声明、身份与文件指纹，不能从字段独立证明平台隔离或测试语义正确。
