# 验收记录的阅读结构与数据维护

## 对使用者的入口

```text
验收记录/
├── 验收记录总.md
├── 验收记录总.html
├── 需求验收记录/
│   ├── 第001轮.md
│   ├── 第001轮.html
│   ├── 第002轮.md
│   ├── 第002轮.html
│   └── .过程/第001轮/…
├── UI验收记录/
├── 原型验收记录/
├── 技术方案验收记录/
├── 代码验收记录/
└── 测试验收记录/
```

只为本项目使用的阶段建立目录。每轮在所属阶段保留一份MD和一份HTML，包括本轮问题、建议、疑问、原始结论、检查证据、未检/排除范围，以及后续答复、处理结果或不处理的解释。发现、主对话答复、修复说明和证据归属同一轮；答复和修复不增加轮次，下一次验收或独立复验才新建轮次。不得把派发尝试误称为已执行验收。

总览按「阶段 → 轮次 → 问题/答复/结果」组织，展示阶段当前状态与确认，以及每轮新发现、新增问题点、重新打开、复验关闭和验收当时未关闭数量；不默认再铺一份跨轮次的完整问题清单。总览和明细来自同一份数据；不是手工维护两套问题列表。默认交付总览入口及相关轮次，不把内部JSON、提示词、快照逐个当成面向使用者的交付物。

## 原始证据与阅读视图

- `.dev-sequence/reviews/验收数据.json`：阶段、轮次和追加答复的机器维护源。交接账本、授权历史也放此处。
- `验收记录/<阶段验收记录>/.过程/第NNN轮/`：本轮请求、一个通用验收提示词、需要时的本模型交接提示词、评审资料包、结果模板、冻结的`原始验收报告.json`、回传与执行证据。
- 无需为请求、提示词、授权和交接日志额外生成HTML。Agent验收只生成一个通用提示词；选择第三方时交付其完整内容即可，不提前生成一套未使用的第三方副本。
- 原始结果JSON和输入快照冻结，不改写历史结论。MD/HTML是可刷新的阅读视图：保留原始发现/结论，并追加呈现带主体、时间和来源轮次的答复及复验，不能用后来处理覆盖当时原文。
- 不处理建议时必须解释理由，解释不等于批准豁免。`fixed`、`answered`、`declined`都不自动成为`verified`或让阻断问题通过。

## HTML 的DOM与数据分离

总览和单轮HTML使用固定的`assets/review-record.html`，在同一个文件内放唯一的安全JSON块：

```html
<script id="ds-review-data" type="application/json">…</script>
```

固定脚本解析该块为`REVIEW_DATA`并生成DOM。日常更新只原子替换这个块，保留其他HTML、CSS和JS，包括项目已定制的页面框架。页面可以离线打开，不依赖fetch、CDN或额外JSON文件；正文用textContent渲染，JSON中的`<`转义，链接仅接受安全本地相对路径。

MD与HTML内容范围一致，使用同样的阶段、轮次、问题与答复层级。HTML支持轮次、问题、答复和证据折叠，以及全部展开/收起；默认展开最新轮次和待处理问题，已关闭历史内容收起。折叠标题保留状态、数量，当前待处理入口始终可见；不能把失败、未检查、失效或豁免省略成通过。页面结构确需升级时另行修改模板和项目壳；不是每次新增记录重新生成DOM源码。

## 追加处理答复

用结构化入口追加，避免手改派生MD或破坏冻结JSON：

```sh
python3 "$CORE_ROOT/scripts/ds.py" --project "$PROJECT_ROOT" reply \
  --stage prd --round 1 --issue DF-001 --by "实际处理者" \
  --disposition declined --message "不处理的具体解释" --evidence "实际决定或依据"
```

`disposition`为`fixed`、`answered`或`declined`。总览和原提出轮次的阅读页会一起展示答复；原始结果不变。修复说明和实际依据继续用reply写回提出轮次（fixed须有evidence），不再建立独立fix轮次。随后新建review轮次，由新上下文复验；用verifications引用原问题ID并给出实际证据，工具将验证事件关联回原记录。工具不会根据一条答复偷偷修改阶段结论。


## 轮次与问题去重

- 新发现使用新ID；同一问题的新问题点沿用ID并标changeType=updated，已关闭问题复发标reopened。独立的新问题使用新ID，可用relatedIssueId关联。
- issues只承载本轮新发现或变化；旧项复验用verifications：issueId、result=pass/fail/not_checked、evidence、comment。工具保留对旧版在issues中回传verified的兼容。
- 复验通过只在本轮简要显示编号、来源轮次、结论和证据，不复制原问题全文；原轮次同时追加本次验证依据。已关闭且本次无异常的项不再列入后续问题清单。
- 旧项未解决时保留简要待处理提示和原轮次链接，有新增问题点才再展开完整条目。遗漏不代表关闭，历史critical/major未独立验证仍阻止通过。
- 回归测试仍按实际影响执行，其通过证据进入检查项；「不重复展示问题」不等于「不再检查」。
- 复发或新增问题点所在轮次可直接reply；答复记录它所依据的最新验收轮次，避免同秒的旧修复被误认为复发后的新修复。原提出轮次仍保留完整处理链。
- 回传时输入已失效，或冻结证据已损坏的通过声明，不能关闭历史阻断项；下一轮仍需独立复验。
- 主对话的fixed/answered/declined只表示处理，不自动关闭。阶段当前结论仍取最新编号轮次，原始结论与后续处理状态分别展示。
- prepare自动冻结尚未关闭的问题原文和实际答复到request.json的priorIssues；评审须先看当前产物再核对历史，不能凭答复判通过。

## 已有项目

读取旧`验收记录/验收数据.json`和旧交接账本时保持兼容；后续机器状态写入新维护位置，新阅读视图按新结构生成。旧冻结文件不自动移动、删除或覆盖，引用和旧哈希仍可查。整理既有项目的遗留文件属于单独迁移工作，需要先盘点引用与当前任务，不因更新skill擅自搬动项目。共享协议变动仍按现行版本绑定规则检查失效，不能把布局调整等同业务复验已通过。

新版不自动合并、删除或重编号旧fix轮次；历史页面标明「历史修复记录」。新版prepare --kind fix会提示改用reply。

旧版默认HTML壳在刷新时先备份再采用新版；已定制的旧壳不会静默覆盖。需要改用新模板时明确执行review-views --upgrade-template，旧页面备份到.dev-sequence/reviews/页面备份/；该命令会采用新版模板，项目定制应从备份中另行保留。新版壳日常仍仅替换内嵌数据块。阅读模板升级不等于业务复验通过，协议变化后的受影响结论仍按版本规则失效。
