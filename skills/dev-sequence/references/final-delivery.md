# 最终交付与工程目录

## 何时生成
用户要求完整流程或完整重做时按六个适用节点形成当轮成果与独立验收。等价输入可复用内容，不自行删去被要求的需求、UI、原型或技术节点。已明确的单阶段/组合任务按其范围交付，不称未执行的完整链路已完成。

开始新迭代时，将上次已由本流程管理的最终交付归档到 `.dev-sequence/delivery-history/`（不改旧冻结记录），不要让旧包继续冒充当前最终版本。未知来源的同名目录先盘点，不直接清空。

项目根 `交付/` 只在 `.dev-sequence/project.json` 声明的本轮所有适用节点最新状态均为 `passed`、确认均为 `accepted` 且指纹一致时生成。pending、stale、失败、暂不验收、豁免都不算全部通过。来源/规则/代码或必要证据变更须重新核对受影响节点；不得只看历史HTML、目录存在或Agent自述。

中间安装包、预览、截图与自检日志放对应节点或 `.dev-sequence/builds/`，不提前放进最终交付。发布、部署和外部发送仍须独立授权。

## 放什么
先定义用途明确的白名单，最终只放用户安装、使用或验核版本所需的内容。例如Chrome扩展默认安装ZIP、独立可读的使用说明、包含包指纹和六节点绑定的交付清单。不机械复制整个项目，也不把需求/UI/原型/技术/验收报告各复制一套到交付。

旧版本、重复截图、测试日志、提示词、临时文件、缓存、未使用资源和开发脚本不进交付。源码是否需要交付由用户目标决定；已有 `代码/` 可直接作为维护源，无需再复制一份。所有被打包或复制的源文件必须纳入最终测试冻结输入且字节一致。压缩包内容、入口、依赖及使用说明应可复核。

## 工具
创建 `.dev-sequence/final-delivery.json`，每个条目包括：`type`（`zip-tree`或`file`）、`source`（项目内路径）、`target`（最终目录内文件名）和非空 `purpose`。不提供覆写节点范围或跳过校验的选项。

```json
{"artifacts":[
 {"type":"zip-tree","source":"代码/src","target":"extension.zip","purpose":"加载已解压的扩展程序"},
 {"type":"file","source":"代码/使用说明.html","target":"使用说明.html","purpose":"安装、迁移与使用"}
]}
```

```sh
python3 "$CORE_ROOT/scripts/finalize_delivery.py" --project "$PROJECT_ROOT" --spec .dev-sequence/final-delivery.json
```

工具在锁内调用真实验收刷新，检查全部节点、确认/指纹及源文件与最终测试快照一致，按白名单从已核对字节生成，最后原子提升为 `交付/`。生成 `交付清单.json` 记录阶段轮次/指纹、测试指纹及产物SHA-256。若输出已存在，拒绝合并覆盖，要求先归档，防止混入旧文件。结构与哈希检查不代替独立功能测试和用途审查。

## 工程目录
新空项目：实施源码/配置、构建脚本、必要测试、运行说明集中 `代码/`；需求、UI、原型、技术、测试及独立验收按各节点维护；根仅项目导航和全局协作/来源文件。
既有仓库保留工程原位；用户要求迁移时才迁移，并修正脚本工作目录、依赖、导入、文档、预览、打包与测试路径。不能把空的 `代码/` 配置壳当实际实施，也不能移动源文件后继续使用旧路径通过结论。
